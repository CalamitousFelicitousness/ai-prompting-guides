# Grok Imagine Image: structure decision and source notes

Not a scrape. Hand-authored 2026-08-15 from the sibling scrapes in this folder: the xAI announcement,
the docs.x.ai capability pages, the full REST reference markdown, and the FAL and WaveSpeed provider
pages.

## 1. New scheme, image only

`grok-imagine-image` is a new guide and a new `prompt_scheme`. Nothing in the set covered xAI before.

It covers the three image models that share one grammar and one pair of endpoints:
`grok-imagine-image-2.0`, `grok-imagine-image-quality`, `grok-imagine-image`. They take the same
request shape, the same single `prompt` string, and the same reference notation. The differences are
quality and capability, which is the merge case.

Video is EXCLUDED. `grok-imagine-video-1.5` and its siblings carry duration, motion phrasing, video
editing, video extension and reference-to-video, which is the large partly-conflicting layer that
splits Wan and FLUX into separate guides. The name `grok-imagine-video` is reserved for that guide.

`grok-2-image` is still served on WaveSpeed but no longer appears in the owner's Imagine docs or model
list. It is left out rather than assumed to share the scheme, since scheme membership needs an owner
statement and there is none.

## 2. The prompt is rewritten before the image model sees it

This is the headline finding and the reason this note exists. It is documented in the owner's own REST
reference, in the `usage` object of BOTH `/v1/images/generations` and `/v1/images/edits`:

> `text_tokens` (integer, required) - Prompt text tokens consumed by the prompt-rewriting (upsampler)
> LLM, including any served from cache.

> `reasoning_tokens` (integer, required) - Reasoning (thinking) tokens generated by the prompt-rewriting
> (upsampler) LLM.

> `text_tokens` (integer, required) - Rewritten-prompt text tokens generated by the prompt-rewriting
> (upsampler) LLM, excluding reasoning tokens.

So an LLM with a reasoning budget rewrites every prompt, on generation and on edit alike. Two
independent corroborations:

- FAL documents its `revised_prompt` response field as "The enhanced prompt that was used to generate
  the image."
- WaveSpeed exposes a "Prompt Enhancer" control on its Grok Imagine image pages.

There is no enhancer toggle in the owner's request body. The full generation request body is
`aspect_ratio`, `model`, `n`, `prompt`, `resolution`, `response_format`, `storage_options`, `user`,
and the edit body adds `image` and `images`. So the rewrite is unconditional through the owner API
while some hosts expose a switch, which is the access-conditioned shape `wan-video` already uses for
`auto_expand_behavior`.

Near-miss worth recording: the rendered REST page shows `"revised_prompt": ""` in its example response,
which reads as evidence that no rewriting happens. The usage fields say otherwise, and they are the
normative part of the same page. An empty field in a canned example is not a measurement.

## 3. The owner demonstrates its own prompt normalization

The image-generation tool page shows Grok turning a user request into an image prompt:

> input: "Generate an image of a corgi surfing a big wave, in the style of a Japanese woodblock print"

> prompt: "A corgi surfing a big wave, Japanese woodblock print style"

The instruction verb is dropped and "in the style of a X" compresses to "X style". Every other prompt
the owner publishes has the same shape: a noun-phrase subject, then the scene, then a trailing style
clause. That is the canonical form the guide teaches, and it is owner-demonstrated rather than inferred.

## 4. Reference notation is real and is zero-indexed

From the `/v1/images/edits` request body, on the `images` array:

> List of input images for multi-reference editing. Mutually exclusive with `image`. When multiple
> images are provided, refer to them as `<IMAGE_0>`, `<IMAGE_1>`, etc. in the prompt.

Angle brackets, uppercase, underscore, zero-indexed. This is the welding mechanism for ONE ROLE PER
INPUT, and it is the one piece of non-natural-language syntax in the scheme. Single-image edits use the
separate `image` field and take no token, so the notation appears only once there is more than one input.

## 5. Owner versus owner on the reference count

The announcement blog:

> Multi-ref editing accepts up to 5 input images in a single generation, removing the need for manual
> compositing.

The API docs, in two places (Imagine overview and the Multi-Image Editing page):

> image editing with up to 3 reference images

> Use up to three source images for a single image edit.

Resolved on the house rule that the API reference governs, because these guides serve agents prompting
through providers and proxies rather than through grok.com. The blog is describing the consumer app.
Neither number enters the guide: reference counts are provider surface and out of scope. The guide
teaches one role per input and lets the host's own docs impose the ceiling.

## 6. Owner versus provider on edit phrasing

WaveSpeed's Pro Tips:

> Describe the desired outcome rather than the process (e.g., "the man wearing a red shirt" instead of
> "change the shirt color to red").

Every edit prompt the owner publishes is the opposite, a plain imperative: "Render this as a pencil
sketch with detailed shading", "Add a hat to this cat.", "Edit this image so it looks like a watercolor
painting."

Resolved on owner authority. The guide teaches the imperative instruction as canonical and records
outcome phrasing as a provider-recommended alternative, attributed to WaveSpeed. Both are plausible in
front of a rewriting LLM, and neither can be settled from published text, so the owner's own examples win.

WaveSpeed's other tip, "Be specific about what to change and what to preserve", needs no adjudication:
it is NAME WHAT MOVES, PIN WHAT STAYS in a provider's words, and corroborates the house principle.

## 7. No negative-prompt field on any surface

Checked in three places and absent from all of them: the owner's full request-body field lists for both
image endpoints, the FAL schema, and the WaveSpeed parameter table. There is also no seed, no guidance
and no style parameter. Exclusions have nowhere to go but the positive prompt.

Community pages assert that Grok Imagine "ignores negative prompts entirely". That may well be true and
is consistent with there being no field, but no owner surface says it, so the guide states the verifiable
half (there is no field, write the end state you want) and does not assert a mechanism.

## 8. Language support is not published

Every prompt and every in-image text example the owner publishes is English. Community write-ups claim
multilingual in-image text. No owner surface supports it, so `languages` records `en` and the guide flags
non-Latin in-image text as untested rather than either promising or denying it. The announcement gallery
includes a Suzhou itinerary infographic and a Chinese ink painting, but alt text is not evidence about
rendered glyphs.

## 9. Quality tiers and the arena snapshot

The owner's own leaderboard snapshot (Aug 7, 2026) lists `grok-imagine-image-2 (low)` above
`grok-imagine-image-quality` on both the Image Edit and Text-to-Image boards. So the new model at its
lower quality setting outranks the previous quality model. Recorded in the guide as a reason not to reach
for the top setting reflexively, phrased without naming the parameter or its enum values.

`grok-imagine-image-quality` is tiered `legacy` because the announcement states 2.0 "is now generally
available as the new Quality Mode", which supersedes it. `grok-imagine-image` stays `budget`: it is the
cheap fast path and is still current.

## 10. Scraping notes

`docs.x.ai` serves a `.md` variant of most pages (append `.md` to the path), and those are far cleaner
than the rendered HTML, which is roughly 90 percent navigation chrome. The rendered model pages are
almost entirely nav and pricing. Prefer the `.md` form.

The rendered REST reference hides optional request fields behind a "Show optional fields" control that
firecrawl cannot expand, so the rendered page shows only `prompt`. The `.md` variant carries the full
field list, which is where the `<IMAGE_0>` notation and the upsampler usage fields were found. A scrape
of the rendered page alone would have missed both.
